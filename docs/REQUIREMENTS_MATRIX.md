## Entity and feature relationships

Auth users → profiles and trusted user_roles. Listings are destinations/enterprises/heritage. Posts contain social/review/comment/feedback content; parent_id provides threads; listing_id connects map/hub/feed/sentiment/RINI. Events reference actors, recipients, posts and listings. Saved items bridge HOME→MAP itineraries. Source records ground public claims. Private feedback is never public sentiment input. Admin mutations create audit events and recipient notifications.

## Phased implementation plan

1. Foundation: models, source-labeled seed data, SQL security, navigation, public pages.
2. Integrated workflow: SDK repository, auth, social, listings, saved places, itineraries, weather, feedback and notifications.
3. Intelligence and management: congestion, sentiment, recommendations, RINI, admin and MFA.
4. Validation: strict build, algorithm tests, browser acceptance, SQL permission tests where runtime permits; document live configuration gaps; reusable environment setup.

## Decisions and ambiguities

- “Hybrid web/mobile” means one responsive browser app, per explicit constraint.
- No credentials means public preview only, never a pretend login or local-only replacement for Supabase writes.
- Demo business profiles and fictional posts are labeled; they are not real endorsements or contact records.
- Unverified fees remain null. Coordinates and destination descriptions require source/precision labels; no new authoritative verification inferred from a link alone.
- Optional AR/tipping/audit demonstrations deferred until core and live security validation are complete.
- Publication/deployment needs a project and account access; source code and build do not establish a deployed HTTPS site.
